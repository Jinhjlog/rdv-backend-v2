# E2E 테스트 시나리오 작성 가이드

## 1. 테스트 유형

이 프로젝트는 두 가지 E2E 테스트를 운영합니다.

| 유형                  | 목적                       | 테스트 파일                    | 스펙 문서                     |
| --------------------- | -------------------------- | ------------------------------ | ----------------------------- |
| **API Contract Test** | 엔드포인트별 블랙박스 검증 | `test/e2e/*.e2e-spec.ts`       | `docs/e2e/p{0-3}-{모듈명}.md` |
| **Scenario Test**     | 사용자 여정 흐름 검증      | `test/scenarios/*.scenario.ts` | `docs/e2e/scenario-{이름}.md` |

### API Contract Test

각 API 엔드포인트가 올바르게 동작하는지 독립적으로 검증합니다. 매 TC마다 DB를 클린하여 테스트 간 의존성이 없습니다.

### Scenario Test

실제 사용자의 업무 흐름을 처음부터 끝까지 검증합니다. 여러 API를 체인으로 연결하여 이전 스텝의 결과를 다음 스텝에서 사용합니다.

실행 방법:

- API Contract Test: `npm run test:e2e`
- Scenario Test: `npm run test:scenarios`

## 3. 문서 구조 템플릿

```markdown
# {모듈명} E2E 테스트 시나리오

> 우선순위: P0 | 관련 컨트롤러: `파일경로`

## 개요

이 모듈의 핵심 비즈니스 흐름을 1~2문장으로 설명합니다.

## 사전 조건 (Preconditions)

| 항목        | 설명                        |
| ----------- | --------------------------- |
| 인증 토큰   | 어떤 역할의 토큰이 필요한지 |
| 선행 데이터 | 사용자, 모임 등             |

## 테스트 시나리오

### TC-{모듈코드}-{번호}: {시나리오 제목}

> **분류**: Happy Path | Error Case | 권한 검증
> **대상 API**: `{HTTP 메서드} {경로}`

**Given** (사전 상태)

- {조건 1}
- {조건 2}

**When** (행동)

- {API 요청 설명}

**Then** (기대 결과)

- 응답 상태: `{HTTP 상태 코드}`
- 응답 본문: {검증할 필드/구조}
```

## 4. E2E 시나리오 선정 원칙

### E2E에 포함할 것

| 분류                   | 필수 여부    | API당 개수          | 설명                                  |
| ---------------------- | ------------ | ------------------- | ------------------------------------- |
| **Happy Path**         | 필수         | 1~2개               | 정상 동작 확인                        |
| **인증/인가 검증**     | 필수         | 컨트롤러당 대표 1개 | 401 확인 (같은 컨트롤러 내 중복 금지) |
| **핵심 비즈니스 규칙** | 해당 시 필수 | 규칙당 1개          | 상태 전이 위반, 소유권, 중복 방지 등  |

### E2E에서 제외할 것 (유닛 테스트 영역)

| 분류               | 예시                              |
| ------------------ | --------------------------------- |
| **입력 검증**      | 필드 누락, 타입 오류, 길이 초과   |
| **Edge Case**      | 빈 문자열, 공백, 잘못된 UUID 형식 |
| **중복 인증 검증** | 같은 컨트롤러 내 반복 401 검증    |

## 5. 시나리오 ID 규칙

```
TC-{모듈코드}-{번호}
```

| 모듈          | 코드 |
| ------------- | ---- |
| 사용자 인증   | AUTH |
| 사용자 프로필 | USER |
| 모임          | GRP  |
| 초대 코드     | INV  |
| 일정          | EVT  |
| 캐릭터        | CHR  |
| 숏 톡         | STK  |
| 위치 추적     | LOC  |
| 알림          | NTF  |
| 디바이스 토큰 | DTK  |
| 앱 버전       | VER  |
| 헬스체크      | HLT  |

예시: `TC-AUTH-001`, `TC-GRP-003`

---

## 6. 역할 정의

| 역할          | 코드     | 설명                            |
| ------------- | -------- | ------------------------------- |
| 인증 사용자   | `User`   | 디바이스 ID로 로그인한 사용자   |
| 비인증 사용자 | `Guest`  | 로그인하지 않은 상태 (공개 API) |
| 모임장        | `Owner`  | 모임의 OWNER 역할 멤버          |
| 일반 멤버     | `Member` | 모임의 MEMBER 역할 멤버         |

---

## 7. Then 검증 원칙

### 검증해야 하는 것

| 대상                    | 예시                           |
| ----------------------- | ------------------------------ |
| **응답 상태 코드**      | `200`, `401`, `404`            |
| **응답 필드 존재 여부** | `accessToken`이 존재하는가     |
| **에러 코드**           | `errorCode: 'GROUP_NOT_FOUND'` |

### 검증하지 말아야 하는 것

| 대상               | 대안                                          |
| ------------------ | --------------------------------------------- |
| **토큰 내부 형식** | 발급된 토큰으로 보호된 API 호출하여 간접 검증 |
| **입력 검증 에러** | DTO/Pipe 유닛 테스트                          |

### DB 부수효과 검증 기준

DB 직접 조회는 아래 두 조건을 **모두** 만족할 때만 허용합니다:

1. API 응답으로 확인할 수 없는 값인가?
2. 비즈니스/보안 요구사항의 핵심인가?

---

## 8. 작성 시 주의사항

1. **한 시나리오 = 한 가지 검증 목적**
2. **구체적인 값 사용**: "유효한 데이터" 대신 실제 예시 값 작성
3. **부수 효과 명시**: DB 변경 등 (7번 기준 충족 시)
4. **실제 코드 참조**: 컨트롤러/DTO 코드를 확인하여 정확한 필드명 반영
5. **테스트 간 독립성**: 매 TC마다 DB 클린, 테스트 순서 의존 금지
