# 알림 생성 및 푸시 알림 전송 전략

> **최종 수정일**: 2026-02-21
> **참고 문서**: `NOTIFICATION_FLOW.md`, `EVENT_FLOW.md`, `GROUP_FLOW.md`, `SHORT_TALK_FLOW.md`, `CHARACTER_FLOW.md`

---

## 1. 기획 원칙

### 거부감 없는 알림의 3가지 조건

1. **"이건 나한테 필요한 정보다"** → 관련성
2. **"지금 알아야 하는 거구나"** → 타이밍
3. **"내가 통제할 수 있다"** → 자율성

### 핵심 규칙

- **자기 행동에 대한 알림 제외**: 본인이 발생시킨 이벤트에 대해서는 알림을 보내지 않는다
- **인앱 알림은 항상 생성, 푸시는 필터링 후 선택적 전송**
- **채팅 메시지는 Notification 테이블에 저장하지 않음** (채팅방에서만 확인)

## 2. 알림 타입 및 등급

### 2-1. notification_type (4종)

모든 알림은 다음 4가지 타입 중 하나로 분류되며, 사용자는 **타입 단위**로 푸시 구독을 ON/OFF 할 수 있다.

| 타입           | 용도                   | 구독 기본값 | 포함 범위                                                            |
| -------------- | ---------------------- | ----------- | -------------------------------------------------------------------- |
| **MEETING**    | 일정 및 모임 관련 알림 | ON          | 일정 생성/수정/삭제, 일정 시작, 출석 결과, 모임 활동, 모임장 이전 등 |
| **CHARACTER**  | 캐릭터 관련 알림       | ON          | 새 캐릭터 획득                                                       |
| **ATTENDANCE** | 앱 출석 관련 알림      | ON          | 앱 접속 기반 출석 이벤트 (향후 확장 예정)                            |
| **SYSTEM**     | 시스템 공지 알림       | ON          | 앱 공지사항, 시스템 점검 안내                                        |

> **참고**: ATTENDANCE 타입은 앱 접속 여부에 따른 출석 이벤트용이며, 일정(Event)의 출석 결과는 MEETING 타입에 포함된다. 현재는 회원가입 시 웰컴 알림에 사용 중이며, 향후 앱 출석 보상 등으로 확장 예정이다.

### 2-2. 알림 등급 (기획 참고용)

모든 이벤트를 **사용자 행동 필요 여부**에 따라 3등급으로 분류한다. 등급은 코드에서 별도 필드로 관리하지 않으며, **기획 참고용**으로만 사용한다. 실제 푸시 전송 여부는 타입별 구독 설정과 푸시 방식(Alert/Silent)으로 제어한다.

| 등급     | 기준             | 인앱 알림 | 푸시 알림     | 예시                    |
| -------- | ---------------- | --------- | ------------- | ----------------------- |
| **긴급** | 지금 행동해야 함 | O         | O (항상)      | 일정 시작, 일정 취소됨  |
| **중요** | 알면 좋은 정보   | O         | O (설정 가능) | 새 일정 생성, 출석 결과 |
| **참고** | 부가 정보        | O         | X (기본 OFF)  | 새 멤버 참여, 멤버 탈퇴 |

## 3. 푸시 전송 방식

### 3-1. Alert 푸시 vs Silent 푸시

| 구분              | Alert 푸시                                               | Silent 푸시                                                |
| ----------------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| **FCM 페이로드**  | `notification` + `data` 포함                             | `data`만 포함                                              |
| **표시 방식**     | 서버에서 title/body 전송, 시스템 알림 트레이에 직접 표시 | 클라이언트 앱이 data를 받아 로컬 알림 생성 및 UI 갱신 처리 |
| **구독 필터링**   | O (`PushDispatchService.sendAlertPushToSubscribers`)     | X (항상 전송, `PushDispatchService.sendSilentPush`)        |
| **사용 시나리오** | 정보 전달이 주 목적 (시스템 공지 등)                     | 앱 상태 동기화 + 클라이언트 측 알림 제어가 필요한 경우     |
| **예시**          | 시스템 공지, 일정 취소                                   | 일정 시작 (위치 공유), 캐릭터 획득                         |

### 3-2. 전송 방식 결정 기준

- **Alert 푸시**: 서버가 알림 내용을 완전히 결정하며, 모든 사용자에게 동일한 형태로 표시
- **Silent 푸시**: 클라이언트가 앱 상태(포그라운드/백그라운드)에 따라 알림 표시 방식을 자율적으로 결정하며, UI 갱신 등 부가 처리가 필요한 경우 사용

| G5  | 멤버 탈퇴               | 참고 | 모임장                     | X         | {닉네임}님이 모임을 떠났어요       | {모임 이름} · 현재 {N}명                         |

### 4-3. 캐릭터(Character) 관련 — `CHARACTER` 타입

| #   | 이벤트         | 등급 | 수신자      | 푸시 방식  | title                                     | subtitle                     |
| --- | -------------- | ---- | ----------- | ---------- | ----------------------------------------- | ---------------------------- |
| C1  | 새 캐릭터 획득 | 중요 | 해당 사용자 | **Silent** | 🎁 새로운 친구 '{캐릭터명}'가 도착했어요! | 캐릭터 컬렉션에서 확인하세요 |

> **C1 참고**: Silent 푸시로 전송되며, 클라이언트 앱이 캐릭터 컬렉션 UI를 갱신하고 로컬 알림을 생성한다. 구독 필터링 없이 항상 전송된다. 도메인 이벤트: `CharacterUnlockedEvent`

### 4-4. 채팅(Short Talk) 관련 — 별도 처리

| #   | 상황                        | 처리 방식                    |
| --- | --------------------------- | ---------------------------- |
| S1  | 앱 포그라운드 + 같은 채팅방 | SSE 실시간 수신 (알림 없음)  |
| S2  | 앱 포그라운드 + 다른 화면   | 인앱 배너 알림 (상단 토스트) |
| S3  | 앱 백그라운드/종료          | 푸시 알림 전송               |

**채팅 푸시 알림 묶음 전략**:

동일 모임에서 **3분 이내** 연속 메시지가 오면 **1개로 묶어서** 전송한다.

| 상황                  | 푸시 내용                                            |
| --------------------- | ---------------------------------------------------- |
| 메시지 1건            | **{모임명}** · {닉네임}: {메시지 내용}               |
| 메시지 2~3건 (3분 내) | **{모임명}** · {닉네임} 외 {N}명이 메시지를 보냈어요 |
| 메시지 4건+ (3분 내)  | **{모임명}** · 새 메시지 {N}개                       |

**채팅과 인앱 알림의 관계**:

- 채팅 메시지는 **인앱 Notification 테이블에 저장하지 않음**
- 채팅 히스토리는 ChatMessage 테이블에서 관리
- 채팅 푸시 알림은 FCM만 전송 (DB 미저장)
- 알림 탭에 채팅 메시지가 섞이면 정보 과부하 → 채팅은 채팅방에서만 확인

### 4-5. 시스템(System) 관련 — `SYSTEM` 타입

| #   | 이벤트           | 등급 | 수신자      | 푸시 방식 | title               | subtitle                      |
| --- | ---------------- | ---- | ----------- | --------- | ------------------- | ----------------------------- |
| Y1  | 앱 공지사항      | 중요 | 전체 사용자 | Alert     | 📢 {공지 제목}      | {공지 요약}                   |
| Y2  | 시스템 점검 안내 | 긴급 | 전체 사용자 | Alert     | 🔧 시스템 점검 안내 | {날짜} {시간} 점검 예정이에요 |

### 4-6. 앱 출석(Attendance) 관련 — `ATTENDANCE` 타입

> 앱 접속 여부에 따른 출석 이벤트로, 향후 확장 예정이다.

| #   | 이벤트      | 등급 | 수신자      | 푸시 방식 | 비고                         |
| --- | ----------- | ---- | ----------- | --------- | ---------------------------- |
| A1  | 웰컴 알림   | -    | 신규 가입자 | X         | 회원가입 시 인앱 알림만 생성 |
| A2  | (향후 정의) | -    | -           | -         | 앱 접속 기반 출석 보상 등    |

> **현재 상태**: 회원가입 시 웰컴 알림(`👋 어디개에 오신 걸 환영해요!`)이 ATTENDANCE 타입 인앱 알림으로 생성된다.

## 6. 푸시 알림 거부감 방지 전략

### 6-1. 온보딩 — 푸시 권한 요청 타이밍

**절대 하지 말 것**: 앱 첫 실행 시 바로 푸시 권한 요청

**권장 플로우**:

```
회원가입 완료
    ↓
첫 모임 참여 또는 첫 일정 참여 시점
    ↓
맥락 있는 권한 요청 화면 표시
    ↓
"일정 시작 전에 알림을 보내드릴까요?
 약속 시간에 늦지 않도록 도와드려요"
    ↓
[알림 받기]  [나중에]
```

- **"나중에"** 선택 시: 다음 일정 참여 시 1회 더 요청, 이후 설정에서만 변경
- **최대 2번**까지만 요청 (3번째부터는 설정 메뉴 안내만)

### 6-2. 조용한 시간 (Quiet Hours) — `Phase 2`

| 항목        | 기본값        | 사용자 설정              |
| ----------- | ------------- | ------------------------ |
| 조용한 시간 | 23:00 ~ 07:00 | 시작/종료 시간 변경 가능 |
| 활성화 여부 | **기본 ON**   | ON/OFF 토글              |

**조용한 시간 중 처리 규칙**:

| 등급                             | 처리                                                                     |
| -------------------------------- | ------------------------------------------------------------------------ |
| **긴급** (일정 시작, 일정 취소)  | **예외: 그대로 전송** — 사용자가 직접 설정한 일정이므로                  |
| **중요** (새 일정, 출석 결과 등) | 인앱 알림만 저장, 푸시는 조용한 시간 종료 후 전송하지 않음 (묵시적 생략) |
| **참고**                         | 인앱 알림만 저장                                                         |
| **채팅**                         | 인앱 알림만 저장, 푸시 미전송                                            |

> **핵심**: 조용한 시간 후 밀린 알림을 한꺼번에 보내면 오히려 거부감 유발 → **밀린 알림은 보내지 않고 인앱에서만 확인**

### 6-3. 빈도 제어 (Rate Limiting) — `Phase 3`

| 카테고리    | 제한 규칙                                |
| ----------- | ---------------------------------------- |
| 채팅        | 동일 모임에서 3분 내 메시지 → 1개로 묶음 |
| 시스템 공지 | 하루 최대 1건                            |
| 동일 이벤트 | 10분 내 동일 유형 중복 전송 방지         |
| 전체        | 1시간 내 최대 10건 (초과 시 인앱만)      |

### 6-4. 모임 규모별 전송 전략 — `Phase 3`

모임 멤버 대상 알림의 발송 범위를 모임 규모에 따라 자동 조절한다.

| 모임 인원 | 전략                                             |
| --------- | ------------------------------------------------ |
| ~10명     | 전원에게 푸시                                    |
| 11~30명   | 전원에게 인앱, 푸시는 최근 활동 멤버만           |
| 31명~     | 전원에게 인앱, 푸시는 일정 참여 이력 있는 멤버만 |

> MVP에서는 10명 이하 모임이 대부분이므로 전원 전송으로 시작

## 7. 알림 구독 설정 설계

### 7-1. 설정 화면 구조

사용자는 `notification_type` 단위(4종)로 푸시 알림 수신 여부를 설정할 수 있다.

```
알림 설정
├── 모임 알림 (MEETING)            [ON]
│   └── 일정 생성/변경/취소, 일정 시작, 출석 결과, 모임 활동 등
├── 캐릭터 알림 (CHARACTER)        [ON]
│   └── 새 캐릭터 획득
├── 출석 알림 (ATTENDANCE)         [ON]
│   └── 앱 접속 기반 이벤트 (향후 확장)
└── 시스템 공지 (SYSTEM)           [ON]
    └── 앱 공지사항, 시스템 점검
```

> **구독 필터링 적용 범위**: Alert 푸시만 구독 설정의 영향을 받는다. Silent 푸시는 앱 상태 동기화 목적이므로 구독 설정과 무관하게 항상 전송된다.

### 7-2. 기본값 전략

| 타입       | 기본값 | 이유                               |
| ---------- | ------ | ---------------------------------- |
| MEETING    | **ON** | 앱의 핵심 가치 (일정 및 모임 관리) |
| CHARACTER  | **ON** | 빈도 낮고 긍정적 경험              |
| ATTENDANCE | **ON** | 향후 확장 대비                     |
| SYSTEM     | **ON** | 중요 공지                          |

> **구독 초기화**: 회원가입 시 `UserRegisteredEvent` 핸들러가 4종 타입 모두 `isSubscribed=true`로 자동 생성한다.

## 9. 푸시 알림 전송 아키텍처

### 9-1. 전체 전송 플로우

```
도메인 이벤트 발생
    ↓
이벤트 핸들러 (notification 모듈 / device-token 모듈)
    ↓
┌──────────────────────────────────────────────────────┐
│ 1. 수신자 목록 결정                                   │
│ 2. 자기 행동 제외 필터링                               │
│ 3. 인앱 알림 생성 (Notification 테이블)                │
│ 4. 푸시 전송 방식 결정                                 │
│    ├─ Alert: 구독 설정 확인 → PushDispatchService      │
│    └─ Silent: 바로 PushDispatchService (구독 무관)     │
│ 5. FCM 전송 + 실패 토큰 자동 삭제                      │
└──────────────────────────────────────────────────────┘
```

### 9-2. 인앱 알림과 푸시 알림의 분리

```
모든 이벤트 → 인앱 알림 (Notification 테이블) : 항상 저장
             ↓
           푸시 전송 방식 결정
             ├─ Alert 푸시
             │   ├── 구독 OFF → 전송 안 함
             │   └── 구독 ON → FCM Alert 전송
             └─ Silent 푸시
                 └── 바로 FCM Silent 전송 (구독 무관)
```

### 9-3. FCM 페이로드 구조

**Alert 푸시** (시스템 공지 등):

```json
{
  "notification": {
    "title": "📢 서비스 점검 안내",
    "body": "2/22(토) 02:00~04:00 점검 예정이에요"
  },
  "data": {
    "type": "SYSTEM",
    "targetScreen": "notifications"
  }
}
```

**Silent 푸시** (일정 시작, 캐릭터 획득 등):

```json
{
  "data": {
    "type": "EVENT_STARTED",
    "eventId": "event-uuid",
    "groupId": "group-uuid"
  }
}
```

```json
{
  "data": {
    "type": "CHARACTER_UNLOCKED",
    "characterCode": "cat",
    "name": "러시"
  }
}
```

## 10. 일정 시작 알림 및 리마인더 전략

현재 일정 시작 시점(`IN_PROGRESS` 전환)에 Silent 푸시 1회 전송. 향후 시작 전 리마인더 확장 가능.

| 시점          | 전송 여부 | 방식   | 내용                       | 구현 상태     |
| ------------- | --------- | ------ | -------------------------- | ------------- |
| 일정 시작 시  | O         | Silent | 🚀 일정이 시작됐어요!      | **구현 완료** |
| -15분 (향후)  | 선택적    | Alert  | 📅 15분 후 일정이 시작돼요 | 미구현        |
| -1시간 (향후) | 선택적    | Alert  | 📅 1시간 후 일정이 있어요  | 미구현        |
| D-1일 (향후)  | 선택적    | Alert  | 📅 내일 일정을 확인하세요  | 미구현        |
